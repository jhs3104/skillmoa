# ADR-0013: 3시간마다 실행해 상한까지 빠르게 채운다

- 상태: 채택
- 날짜: 2026-11-02

## 맥락

목록 구조를 바꿔(ADR-0012) 상한을 19,000개로 올릴 수 있게 됐다. 하루 한 번 실행으로는 상한까지 몇 주가 걸린다. 한 실행은 Actions 제한과 커밋 시점 때문에 무한정 길게 돌릴 수 없다. 상태는 작업이 정상으로 끝날 때 커밋되므로, 시간 초과로 끊기면 그 실행의 결과를 잃는다.

## 결정

- 예약 실행은 3시간마다 돈다. 첫 묶음은 수동으로 돌려 검수한 뒤 예약을 켠다.
- 한 번 실행에 1,000개까지 요약한다. 시간 안에 끝나도록 묶음을 나눈 것이다.
- 하루 호출 상한은 8,000회다.
- 코드 검색이 들어가는 `weekly` 모드는 일요일 18시 UTC 실행 한 번만 쓴다.

첫 실행이 저장소 스캔만으로 5시간 50분 제한을 넘겨 결과를 모두 잃었다. 스킬 수천 개짜리 저장소까지 전부 읽어 GitHub 호출 한도를 썼기 때문이다. 그래서 다음을 더했다.

- 저장소마다 저장소당 상한의 2배까지만 읽는다. 어차피 그 이상은 목록에 실리지 않는다.
- 스캔은 실행당 120분까지만 한다. 남은 저장소는 다음 실행이 이어받는다.
- 수집 단계를 320분에 끊고, 그래도 중간 상태를 커밋한다.

## 검토한 대안

| 대안 | 장점 | 기각 이유 |
|---|---|---|
| 하루 1회 1,000개 | 단순하다 | 19,000개까지 19일 걸린다 |
| 한 번에 19,000개 | 바로 채운다 | 약 21시간이라 Actions 제한을 넘고 끊기면 결과를 잃는다 |
| 주 1회 | 조용하다 | 상한을 채우는 데 맞지 않는다 |

## 결과

- 후보가 충분하면 약 3일에 상한에 닿는다. 전체 요약 비용은 약 $23으로 추정한다.
- 실행마다 데이터 커밋과 재배포가 생긴다. 바뀐 것이 없으면 커밋하지 않는다.
- 후보가 모자라면 상한에 못 미친다. 저장소당 10개 상한이 있어 19,000개를 채우려면 저장소 1,900개 이상이 필요하다.
- 상한을 채운 뒤에는 주기를 다시 늘릴 수 있다.

## 추가 결정 (2026-11-03): 요약 호출을 동시에 보낸다

첫 실측에서 요약 1,000건이 한 건씩 차례로 약 1시간 43분 걸렸다(건당 약 6초). 요약 호출은 서로 독립이라 `[summary] concurrency`(기본 4)개를 동시에 보낸다.

- API 호출만 작업 스레드에서 보내고, 원문 읽기와 상태 기록은 한 스레드에서 한다. 상태에 잠금이 필요 없다.
- 호출 상한은 보낸 호출 수로 센다. 동시에 보내도 실행당·하루 상한을 넘지 않는다.
- 요약 서비스 오류가 나면 새 호출을 멈추고, 이미 보낸 호출은 받아서 기록한다.
- Message Batches API(비동기, 50% 할인)는 쓰지 않는다. 결과가 최대 24시간 뒤에 오고, 응답마다 검사해 다시 요청하는 지금의 재시도 흐름과 맞지 않는다. 비용은 1,000건에 약 $1.6이라 절감 폭이 작다.
- 분당 한도(429)에 닿으면 SDK가 기다렸다 다시 보내고, 그래도 실패하면 이번 실행의 요약을 멈춘다. 그때는 `concurrency`를 낮춘다.
