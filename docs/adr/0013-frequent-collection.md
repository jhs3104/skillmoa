# ADR-0013: 3시간마다 실행해 상한까지 빠르게 채운다

- 상태: 채택
- 날짜: 2026-11-02

## 맥락

목록 구조를 바꿔(ADR-0012) 상한을 19,000개로 올릴 수 있게 됐다. 하루 한 번 실행으로는 상한까지 몇 주가 걸린다. 한 실행은 Actions 제한과 커밋 시점 때문에 무한정 길게 돌릴 수 없다. 상태는 작업이 정상으로 끝날 때 커밋되므로, 시간 초과로 끊기면 그 실행의 결과를 잃는다.

## 결정

- 예약 실행은 3시간마다 돈다. 첫 묶음은 수동으로 돌려 검수한 뒤 예약을 켠다.
- 한 번 실행에 1,000개까지 요약한다. 시간 안에 끝나도록 묶음을 나눈 것이다.
- 하루 호출 상한은 8,000회다.
- 코드 검색이 들어가는 `weekly` 모드는 주 1회만 쓴다. 고르는 방법은 아래 2026-11-08 추가 결정으로 바꿨다.

첫 실행이 저장소 스캔만으로 5시간 50분 제한을 넘겨 결과를 모두 잃었다. 스킬 수천 개짜리 저장소까지 전부 읽어 GitHub 호출 한도를 썼기 때문이다. 그래서 다음을 더했다.

- 저장소마다 저장소당 상한의 2배까지만 읽는다. 어차피 그 이상은 목록에 실리지 않는다.
- 스캔은 실행당 120분까지만 한다. 남은 저장소는 다음 실행이 이어받는다.
- 수집 단계를 320분에 끊고, 그래도 중간 상태를 커밋한다.

## 검토한 대안

| 대안 | 장점 | 기각 이유 |
|---|---|---|
| 하루 1회 1,000개 | 단순하다 | 19,000개까지 19일 걸린다 |
| 한 번에 19,000개 | 바로 채운다 | 약 21시간이라 Actions 제한을 넘고 끊기면 결과를 잃는다 |
| 주 1회 | 조용하다 | 상한을 채우는 데 맞지 않는다 |

## 결과

- 후보가 충분하면 약 3일에 상한에 닿는다. 전체 요약 비용은 약 $23으로 추정한다.
- 실행마다 데이터 커밋과 재배포가 생긴다. 바뀐 것이 없으면 커밋하지 않는다.
- 후보가 모자라면 상한에 못 미친다. 저장소당 10개 상한이 있어 19,000개를 채우려면 저장소 1,900개 이상이 필요하다.
- 상한을 채운 뒤에는 주기를 다시 늘릴 수 있다.

## 추가 결정 (2026-11-03): 요약 호출을 동시에 보낸다

첫 실측에서 요약 1,000건이 한 건씩 차례로 약 1시간 43분 걸렸다(건당 약 6초). 요약 호출은 서로 독립이라 `[summary] concurrency`(기본 4)개를 동시에 보낸다.

- API 호출만 작업 스레드에서 보내고, 원문 읽기와 상태 기록은 한 스레드에서 한다. 상태에 잠금이 필요 없다.
- 호출 상한은 보낸 호출 수로 센다. 동시에 보내도 실행당·하루 상한을 넘지 않는다.
- 요약 서비스 오류가 나면 새 호출을 멈추고, 이미 보낸 호출은 받아서 기록한다.
- Message Batches API(비동기, 50% 할인)는 쓰지 않는다. 결과가 최대 24시간 뒤에 오고, 응답마다 검사해 다시 요청하는 지금의 재시도 흐름과 맞지 않는다. 비용은 1,000건에 약 $1.6이라 절감 폭이 작다.
- 분당 한도(429)에 닿으면 SDK가 기다렸다 다시 보내고, 그래도 실패하면 이번 실행의 요약을 멈춘다. 그때는 `concurrency`를 낮춘다.

## 추가 결정 (2026-11-04): 실행당 요약을 2,500건으로 올린다

예약을 켠 첫날, 3시간 간격 예약 7번 중 3번만 실행됐고 시작도 최대 3시간 늦었다. GitHub는 부하가 높으면 예약 실행을 늦추거나 건너뛴다. 동시 호출로 1,000건 실행이 약 40분으로 줄었고 429 응답은 한 번도 없었으므로, 실행당 상한을 2,500건으로 올려 빠지는 실행을 메운다. 한 번에 약 1시간 20분 걸려 단계 제한(320분) 안에 충분히 들어간다. 하루 상한(8,000건)은 그대로 둔다.

## 추가 결정 (2026-11-08): weekly는 시각이 아니라 지난 날짜로 고른다

처음에는 예약 실행이 일요일 18시(UTC)에 시작될 때만 `weekly`로 바꿨다. 실제 예약 실행은 하루 2~3번뿐이었고 시작 시각도 01:35, 10:59, 19:27처럼 들쭉날쭉했다. 정해 둔 시각에 걸리지 않으면 그 주에는 코드 검색이 돌지 않는다. 11월 5일 수동 실행 뒤로 전체 탐색이 한 번도 돌지 않았고, 스킬 수는 6,860개 근처에서 하루 몇 개씩만 늘었다. 토픽을 달지 않은 저장소는 코드 검색으로만 찾을 수 있다.

- 전체 탐색을 마친 날을 `collector/state/meta.json`의 `last_full_scan_on`에 남긴다.
- 모드를 지정하지 않은 실행은 이 날짜에서 `[discovery] full_scan_interval_days`(7일)가 지났으면 `weekly`가 된다. 기록이 없으면 바로 돈다.
- 코드 검색이 레이트 리밋으로 끊기거나 토큰이 없어 건너뛰면 날짜를 남기지 않는다. 다음 실행이 다시 맡는다.
- `--limit` 실행은 상태가 비어 있어도 전체 탐색을 하지 않는다.

| 대안 | 기각 이유 |
|---|---|
| weekly 전용 cron을 따로 둔다 | 예약 실행은 늦거나 빠질 수 있어 같은 문제가 남는다 |
| 일요일이면 시간 상관없이 첫 실행 | 일요일 실행이 모두 빠지면 그 주는 그대로 건너뛴다 |

## 추가 결정 (2026-11-09): 코드 검색을 여러 실행에 나눠 이어서 읽는다

weekly 전환을 고친 뒤 코드 검색이 처음으로 끝까지 돌았다. 그런데 한 번도 끝나지 못했다. 처음 세 번은 페이지 계산 실수로 요청한 11번째 페이지가 422로 거부되어 약 2시간 반 만에 멈췄다. 그걸 고치자 다음 세 번은 5시간 넘게 코드 검색만 하다가 단계 제한(320분)에 걸려 강제 종료됐다. 한 실행에서 약 4,500번을 요청했는데도 끝나지 않았다. 코드 검색은 분당 10회로 제한되므로 SKILL.md 전체를 한 실행에 읽을 수 없다. 끝나지 않은 실행은 찾은 저장소를 하나도 남기지 못했고, 날짜도 남지 않아 다음 실행이 다시 처음부터 시작했다. 그동안 스캔과 요약은 한 번도 돌지 못했다.

- 실행마다 코드 검색은 `[discovery] code_search_minutes`(90분)까지만 한다. 아직 읽지 않은 크기 범위는 `meta.json`의 `code_search_pending`에 남기고, 다음 실행이 이어서 읽는다.
- 남은 범위가 있으면 날짜와 상관없이 그 실행은 `weekly`가 된다. 남은 범위가 없어진 날을 `last_full_scan_on`으로 남긴다.
- 찾은 저장소는 그 실행에서 바로 등록하고 스캔한다. 코드 검색 90분, 스캔 120분, 요약을 합쳐도 320분 안에 든다.
- 한 범위가 실패하면 그 범위만 건너뛴다. 레이트 리밋에 걸리면 그 범위를 남은 범위에 다시 넣고 멈춘다.
- 매 실행이 앞으로 나아가도록 첫 범위는 시간과 상관없이 읽는다.

| 대안 | 기각 이유 |
|---|---|
| 단계 제한을 늘린다 | 작업 제한(6시간)에 가깝고, 그래도 끝난다는 보장이 없다 |
| 범위마다 첫 페이지만 읽는다 | 요청은 줄지만 한 범위에서 100건 뒤의 저장소를 놓친다 |
| 코드 검색 전용 워크플로를 따로 둔다 | 상태 파일을 두 워크플로가 함께 고치게 되어 커밋이 충돌한다 |

### 실행 전체에 마감을 둔다

코드 검색을 90분으로 나눠도 단계별 예산을 더하면 320분을 넘을 수 있다. 과거 가장 무거운 실행은 요약 2,184건과 분류 3,000건에 85분이 걸렸고, 요약과 분류에는 시간 제한이 없었다. GitHub 한도가 바닥나면 한 번에 최대 약 1시간을 기다린다. 갱신 10분, 코드 검색 90분, 스캔 120분, 한도 대기 60분, 요약·분류 95분을 더하면 375분이다.

- `[run] max_minutes`(285분)를 실행 전체의 마감으로 둔다. 단계 제한보다 35분 앞이라 진행 중인 호출을 받고 상태를 저장해 내보낼 시간이 남는다.
- 코드 검색과 스캔은 자기 예산과 실행 마감 중 이른 쪽에서 멈춘다.
- 요약과 분류는 마감이 지나면 새 호출을 보내지 않는다. 남은 것은 다음 실행이 맡는다.
- GitHub 한도 대기가 마감을 넘으면 기다리지 않고 수집을 멈춘다. 이미 처리한 것은 저장한다.
- 마감으로 멈춘 실행은 지표의 `stopped_by_time`으로 알 수 있다.
